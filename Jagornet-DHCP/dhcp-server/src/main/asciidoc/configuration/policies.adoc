=== Server Policies
Server polices are configured using the `polices` element. 
Each `policyList` element consists of `name` and `value` elements. For example:

.xml
----
<policies>  
  <policyList>
    <name>ha.role</name>
    <value>primary</value>
  </policyList>
  <policyList>
    <name>ha.peerServer</name>
    <value>10.0.0.20</value>
  </policyList>
</policies>
----

.json
----
"policies" : {
  "policyList" : [ {
    "name" : "ha.role",
    "value" : "primary"
  },
  {
    "name" : "ha.peerServer",
    "value" : "10.0.0.20"
  } ]
}
----

.yaml
----
policies:
  policyList:
  - name: "ha.role"
    value: "primary"
  - name: "ha.peerServer"
    value: "10.0.0.20"
----

The sections below describe the configuration policies available for the Jagornet DHCP Server. 
The Hierarchy list indicates which levels of the configuration hierarchy 
the policy is supported. For policies that are supported at 'all' levels, the lower 
level policy overrides the value of any matching higher level policy.
 
=== Channel Resource Policies
Channels are used for processing all incoming network requests. The following _expert_ policies can be adjusted if necessary.

==== Policy: channel.threadPoolSize (Thread Pool Size)
- Name: `channel.threadPoolSize`
- Default: `16`
- Description: The size of the Netty thread pool allocated for network channel request processing.
- Hierarchy: global

==== Policy: channel.readBufferSize (Read Buffer Size)
- Name: `channel.readBufferSize`
- Default: `307200`
- Description: The size, in bytes, of the network channel socket read buffer for receiving incoming DHCP packets.
- Hierarchy: global

==== Policy: channel.writeBufferSize (Write Buffer Size)
- Name: `channel.writeBufferSize`
- Default: `307200`
- Description: The size, in bytes, of the network channel socket write buffer for transmitting outgoing DHCP responses.
- Hierarchy: global

=== Lease Database Policies
The lease information is stored in a supported JDBC database. The following 
_expert_ policies can be adjusted if necessary.

==== Policy: database.schemaType (Schema Type)
- Name: `database.schemaType`
- Default: `jdbc-h2`
- Description: The lease database schema and persistence backend type. Supported options:

* `jdbc-h2` - uses JDBC to access an embedded H2 database for lease bindings (default).
* `jdbc-derby` - uses JDBC to access an embedded Apache Derby database for lease bindings.
* `jdbc-sqlite` - uses JDBC to access an embedded SQLite database for lease bindings.
* `jdbc-postgres` - uses JDBC to access an external PostgreSQL database for lease bindings.
* `jdbc-mysql` - uses JDBC to access an external MySQL or MariaDB database for lease bindings.
* `jdbc-mariadb` - alias for `jdbc-mysql`.

- Hierarchy: global

==== Policy: database.schemaVersion (Schema Version)
- Name: `database.schemaVersion`
- Default: `2`
- Description: The lease database schema version. Version 1 schema uses the deprecated relational model and can only be used with the `jdbc-*` schema types. Version 2 uses a high-performance single-table model and can be used with all schema types.
- Hierarchy: global

=== Binding Manager Policies
The binding manager is responsible for lease binding lifecycle maintenance. The following 
_expert_ policies can be adjusted if necessary.

==== Policy: binding.manager.reaper.startupDelay (Reaper Startup Delay)
- Name: `binding.manager.reaper.startupDelay`
- Default: `10000`
- Description: Number of milliseconds for the background reaper thread to wait after server startup before performing the initial scan for expired lease bindings. Note that bindings are always expired on demand when needed to free them for assignment.
- Hierarchy: global

==== Policy: binding.manager.reaper.runPeriod (Reaper Run Period)
- Name: `binding.manager.reaper.runPeriod`
- Default: `60000`
- Description: Number of milliseconds for the background reaper thread to wait between periodic checks for expired lease bindings.
- Hierarchy: global

==== Policy: binding.manager.offerExpiration (Offer Expiration)
- Name: `binding.manager.offerExpiration`
- Default: `12000`
- Description: Number of milliseconds after which an offered IP address is considered expired and returned to the free pool if the client does not complete the lease request.
- Hierarchy: global

==== Policy: binding.manager.deleteOldBindings (Delete Old Bindings)
- Name: `binding.manager.deleteOldBindings`
- Default: `false`
- Description: Flag indicating whether the server should permanently delete lease bindings upon expiration, or keep the binding record in the database marked as expired.
- Hierarchy: global

=== Dynamic DNS Update Policies
Jagornet DHCP Server supports standard Dynamic DNS Update mechanisms defined by
the following IETF RFCs:

* http://www.ietf.org/rfc/rfc4702.txt[RFC 4702]
* http://www.ietf.org/rfc/rfc4703.txt[RFC 4703]
* http://www.ietf.org/rfc/rfc4704.txt[RFC 4704]

The following policies configure Dynamic DNS update processing.

==== Policy: ddns.mode (DDNS Mode)
- Name: `ddns.mode`
- Default: `disabled`
- Description: Controls Dynamic DNS (DDNS) update delegation between the DHCP server and clients. Available values:

* `disabled` - no DDNS updates performed.
* `server` - server performs both forward (A/AAAA) and reverse (PTR) updates, overriding client requests if needed.
* `client` - server honors client FQDN flags. If client requests not to update (N flag), no updates are performed. If client requests to perform forward updates (S=0), server updates only reverse (PTR) records.

- Hierarchy: all

NOTE: The legacy policy `ddns.update` (`none`, `server`, `honorNoUpdate`, `honorNoA`, `honorNoAAAA`) is retained for backward compatibility and is automatically mapped to `ddns.mode`.

==== Policy: ddns.record.type (DDNS Record Type)
- Name: `ddns.record.type`
- Default: `dhcid`
- Description: Specifies the identification resource record type published in forward DNS zones during DDNS updates:

* `dhcid` - RFC 4701 standard DHCID resource record (RR type 49).
* `txt` - Legacy ISC DHCP "interim" style TXT resource record (RR type 16), facilitating migration from ISC DHCP environments.

- Hierarchy: all

==== Policy: ddns.conflict.strategy (DDNS Conflict Strategy)
- Name: `ddns.conflict.strategy`
- Default: `strict`
- Description: Controls the conflict resolution strategy used during forward DNS updates:

* `strict` - RFC 4703 client ownership. The first registrant owns the FQDN; other dynamic clients cannot overwrite or claim it.
* `replace-dynamic` - Dynamic client takeover with static host protection. Dynamic clients can displace other dynamic client entries (identified via a shared dynamic token), while strictly protecting static infrastructure records (servers, routers, printers) that lack the dynamic marker.
* `unconditional` - Blind replace without prerequisites (equivalent to ISC DHCP `update-conflict-detection false`).

- Hierarchy: all

==== Policy: ddns.dynamic.token (DDNS Dynamic Token)
- Name: `ddns.dynamic.token`
- Default: `dynamic`
- Description: The marker string embedded in TXT or DHCID records when `ddns.conflict.strategy` is set to `replace-dynamic` to distinguish dynamic client registrations from static infrastructure.
- Hierarchy: all

==== Policy: ddns.synchronize (DDNS Synchronize)
- Name: `ddns.synchronize`
- Default: `false`
- Description: Flag indicating whether the DHCP server should synchronize DDNS updates with issuing of leases. When `true`, the DHCP Reply message is held until the DDNS update completes. When `false` (default), DDNS updates are queued and performed asynchronously.
- Hierarchy: all

==== Policy: ddns.domain (DDNS Domain)
- Name: `ddns.domain`
- Description: The default DNS domain suffix to append to unqualified client hostnames to form a Fully Qualified Domain Name (FQDN) for DDNS updates. If the client FQDN already contains a domain name, that domain name (everything after the first label) is replaced by this configured domain.
- Hierarchy: all

==== Policy: ddns.ttl (DDNS TTL)
- Name: `ddns.ttl`
- Default: `0.3`
- Description: Time-to-Live (TTL) for DDNS updates. If the value is less than 1.0, it is calculated as a fraction of the client lease valid lifetime in seconds (e.g. `0.3` = 30% of lease time). If 1.0 or greater, it represents an absolute number of seconds.
- Hierarchy: all

==== Policy: ddns.server (DDNS Server)
- Name: `ddns.server`
- Description: The IP address or hostname of the dynamic DNS server for sending DDNS updates.
- Hierarchy: all

==== Policy: ddns.tsig.keyName (TSIG Key Name)
- Name: `ddns.tsig.keyName`
- Description: The key name identifier for TSIG (Transaction Signature, RFC 2845) authenticated DDNS updates.
- Hierarchy: all

==== Policy: ddns.tsig.algorithm (TSIG Algorithm)
- Name: `ddns.tsig.algorithm`
- Description: The cryptographic algorithm name used for TSIG-signed DDNS updates. Currently supported value is `hmac-sha256`.
- Hierarchy: all

==== Policy: ddns.tsig.keyData (TSIG Key Data)
- Name: `ddns.tsig.keyData`
- Description: The base64-encoded shared secret key data used for TSIG-signed DDNS updates.
- Hierarchy: all

==== Policy: ddns.forward.zone.name (Forward Zone Name)
- Name: `ddns.forward.zone.name`
- Description: The name of the dynamic DNS zone for forward (A/AAAA) updates. If not set, the forward zone name is automatically determined in order of precedence: (1) `ddns.domain` policy value, (2) domain configured for client (Option 15 `v4DomainNameOption` or Option 24 `v6DomainSearchListOption`), or (3) domain portion of client-supplied FQDN.
- Hierarchy: all

==== Policy: ddns.forward.zone.ttl (Forward Zone TTL)
- Name: `ddns.forward.zone.ttl`
- Default: `0.3`
- Description: Time-to-Live (TTL) specific to forward zone DDNS updates. Overrides `ddns.ttl` for forward updates. Values < 1.0 represent lease percentage; values >= 1.0 represent absolute seconds.
- Hierarchy: all

==== Policy: ddns.forward.zone.server (Forward Zone Server)
- Name: `ddns.forward.zone.server`
- Description: The IP address or hostname of the dynamic DNS server for sending forward zone DDNS updates. Overrides `ddns.server` for forward updates.
- Hierarchy: all

==== Policy: ddns.forward.zone.tsig.keyName (Forward Zone TSIG Key Name)
- Name: `ddns.forward.zone.tsig.keyName`
- Description: The TSIG key name for signed forward zone DDNS updates. Overrides `ddns.tsig.keyName` for forward updates.
- Hierarchy: all

==== Policy: ddns.forward.zone.tsig.algorithm (Forward Zone TSIG Algorithm)
- Name: `ddns.forward.zone.tsig.algorithm`
- Description: The TSIG algorithm name for signed forward zone DDNS updates. Overrides `ddns.tsig.algorithm` for forward updates. Currently supported value is `hmac-sha256`.
- Hierarchy: all

==== Policy: ddns.forward.zone.tsig.keyData (Forward Zone TSIG Key Data)
- Name: `ddns.forward.zone.tsig.keyData`
- Description: The base64-encoded TSIG key data for signed forward zone DDNS updates. Overrides `ddns.tsig.keyData` for forward updates.
- Hierarchy: all

==== Policy: ddns.reverse.zone.name (Reverse Zone Name)
- Name: `ddns.reverse.zone.name`
- Description: The name of the dynamic DNS zone for reverse (PTR) updates. If not set, the reverse zone is automatically calculated from the client's subnet address and prefix length (`in-addr.arpa.` for IPv4 octet-aligned subnets, or `ip6.arpa.` for IPv6 nibble-aligned subnets).
- Hierarchy: all

==== Policy: ddns.reverse.zone.bitLength (Reverse Zone Bit Length)
- Name: `ddns.reverse.zone.bitLength`
- Default: `0`
- Description: The number of bits representing the subnet prefix length for calculating reverse zone names. When set to `0` (default), the subnet prefix length of the pool or link is used.
- Hierarchy: all

==== Policy: ddns.reverse.zone.ttl (Reverse Zone TTL)
- Name: `ddns.reverse.zone.ttl`
- Default: `0.3`
- Description: Time-to-Live (TTL) specific to reverse zone DDNS updates. Overrides `ddns.ttl` for reverse updates. Values < 1.0 represent lease percentage; values >= 1.0 represent absolute seconds.
- Hierarchy: all

==== Policy: ddns.reverse.zone.server (Reverse Zone Server)
- Name: `ddns.reverse.zone.server`
- Description: The IP address or hostname of the dynamic DNS server for sending reverse zone DDNS updates. Overrides `ddns.server` for reverse updates.
- Hierarchy: all

==== Policy: ddns.reverse.zone.tsig.keyName (Reverse Zone TSIG Key Name)
- Name: `ddns.reverse.zone.tsig.keyName`
- Description: The TSIG key name for signed reverse zone DDNS updates. Overrides `ddns.tsig.keyName` for reverse updates.
- Hierarchy: all

==== Policy: ddns.reverse.zone.tsig.algorithm (Reverse Zone TSIG Algorithm)
- Name: `ddns.reverse.zone.tsig.algorithm`
- Description: The TSIG algorithm name for signed reverse zone DDNS updates. Overrides `ddns.tsig.algorithm` for reverse updates. Currently supported value is `hmac-sha256`.
- Hierarchy: all

==== Policy: ddns.reverse.zone.tsig.keyData (Reverse Zone TSIG Key Data)
- Name: `ddns.reverse.zone.tsig.keyData`
- Description: The base64-encoded TSIG key data for signed reverse zone DDNS updates. Overrides `ddns.tsig.keyData` for reverse updates.
- Hierarchy: all

=== Hostname Policies
Policies controlling client hostname validation, scrubbing for DNS compliance (RFC 952, RFC 1123, RFC 1035), and automatic hostname generation. These policies can be configured globally, per link, per pool, or per filter.

==== Policy: hostname.mode (Hostname Mode)
- Name: `hostname.mode`
- Default: `as-is`
- Description: Hostname processing strategy for client identification and DDNS updates. Supported values:

* `as-is` - Use client-supplied hostname/FQDN unmodified (existing default behavior).
* `scrub` - Validate and sanitize client-supplied hostname for DNS compliance. Drops hostname if invalid.
* `scrub-or-generate` - Validate and sanitize client hostname; if absent or invalid, generate a compliant hostname.
* `always-generate` - Ignore client-supplied hostname and always generate a compliant hostname from template.
* `disabled` - Disable hostname and DDNS processing for matching clients.

- Hierarchy: all

==== Policy: hostname.generate.template (Hostname Generation Template)
- Name: `hostname.generate.template`
- Default: `host-${ip.dashed}`
- Description: Template string used when generating hostnames for clients. Supported tokens: `${ip}` (IP address), `${ip.dashed}` (IP address with hyphens instead of dots/colons), `${ip.hex}` (hexadecimal IP), `${mac}` (MAC address in hex), `${mac.dashed}` (MAC address with hyphens), `${duid}` (client DUID in hex), and `${filter.name}` (name of matching filter).
- Hierarchy: all

==== Policy: hostname.scrub.allowUnderscores (Hostname Scrub Allow Underscores)
- Name: `hostname.scrub.allowUnderscores`
- Default: `false`
- Description: Controls whether underscores (`_`) should be preserved in sanitized hostnames. When `false`, underscores are converted to the replacement character (default `-`) for strict DNS RFC compliance.
- Hierarchy: all

==== Policy: hostname.scrub.replaceChar (Hostname Scrub Replacement Character)
- Name: `hostname.scrub.replaceChar`
- Default: `-`
- Description: Character substituted for non-compliant DNS characters during hostname scrubbing.
- Hierarchy: all

==== Policy: hostname.scrub.collapseHyphens (Hostname Scrub Collapse Hyphens)
- Name: `hostname.scrub.collapseHyphens`
- Default: `true`
- Description: Controls whether consecutive hyphens (`--+`) in sanitized hostnames should be collapsed into a single hyphen (`-`).
- Hierarchy: all

==== Policy: hostname.scrub.stripDomains (Hostname Scrub Strip Domains)
- Name: `hostname.scrub.stripDomains`
- Default: `local,lan,home`
- Description: Comma-separated list of ad-hoc or mDNS domain suffixes to strip from client-supplied hostnames during sanitization.
- Hierarchy: all

==== Policy: hostname.sendOption12 (Hostname Send Option 12)
- Name: `hostname.sendOption12`
- Default: `on-change`
- Description: Controls when DHCPv4 Option 12 (Host Name) is returned in DHCPOFFER and DHCPACK messages. Supported values: `on-change` (return Option 12 when hostname was altered or generated), `always`, `never`, and `if-requested` (only if client requested Option 12 in Parameter Request List).
- Hierarchy: all

=== DHCP Protocol Policies
The DHCP protocol handler follows IETF standards. However, in test labs or
specialized environments, it may be desirable to modify certain behavior. The following 
_expert_ policies can be adjusted if necessary.

==== Policy: dhcp.ignoreLoopback (Ignore Loopback)
- Name: `dhcp.ignoreLoopback`
- Default: `true`
- Description: Configures whether the DHCP server ignores loopback network interfaces when binding sockets during server startup.
- Hierarchy: global

==== Policy: dhcp.ignoreLinkLocal (Ignore Link Local)
- Name: `dhcp.ignoreLinkLocal`
- Default: `true`
- Description: Configures whether the DHCP server ignores IPv4 link-local (169.254.0.0/16) and IPv6 link-local (fe80::/10) addresses when binding sockets during server startup.
- Hierarchy: global

==== Policy: dhcp.ignoreSelfPackets (Ignore Self Packets)
- Name: `dhcp.ignoreSelfPackets`
- Default: `true`
- Description: Configures whether the DHCP server discards packets received from one of the server's own local IP addresses to prevent feedback loops.
- Hierarchy: global

==== Policy: dhcp.processor.recentMessageTimer (Recent Message Timer)
- Name: `dhcp.processor.recentMessageTimer`
- Default: `5000`
- Description: Number of milliseconds to retain transaction state for recently processed client messages to mitigate replay attacks and duplicate packet processing (DoS protection).
- Hierarchy: global

==== Policy: dhcp.sendRequestedOptionsOnly (Send Requested Options Only)
- Name: `dhcp.sendRequestedOptionsOnly`
- Default: `false`
- Description: Flag indicating whether the DHCP server returns only options explicitly requested by the client in its Option Request Option / Parameter Request List, or includes all configured options.
- Hierarchy: all

==== Policy: dhcp.supportRapidCommit (Support Rapid Commit)
- Name: `dhcp.supportRapidCommit`
- Default: `false`
- Description: Flag indicating whether the DHCP server honors 2-message DHCPv6 Rapid Commit exchanges (SOLICIT -> REPLY, RFC 8415 / RFC 3315).
- Hierarchy: global, filter, link, linkFilter

=== DHCPv4 Policies
The following policies configure DHCPv4-specific behaviors and filtering.

==== Policy: v4.header.sname (Header: Server Name)
- Name: `v4.header.sname`
- Description: Populates the optional `sname` (server host name) field in the fixed DHCPv4 message header. Typically used in network boot environments (PXE/TFTP). See also `v4TftpServerNameOption` (Option 66).
- Hierarchy: all

==== Policy: v4.header.filename (Header: Bootfile Name)
- Name: `v4.header.filename`
- Description: Populates the optional `file` (boot file name) field in the fixed DHCPv4 message header. Specifies the boot image file path which the client retrieves from the TFTP server. See also `v4BootFileNameOption` (Option 67).
- Hierarchy: all

==== Policy: v4.ignoredMacAddrs (Ignored MAC Addresses)
- Name: `v4.ignoredMacAddrs`
- Default: `000000000000, FFFFFFFFFFFF`
- Description: Comma-separated list of client MAC addresses that the DHCPv4 server will silently ignore.
- Hierarchy: all

==== Policy: v4.excludedMacAddrsFile (Excluded MAC Addresses File)
- Name: `v4.excludedMacAddrsFile`
- Default: empty
- Description: Path to a file containing MAC addresses to ignore/exclude from DHCPv4 service (denylist). Relative paths are resolved against `$JAGORNET_DHCP_HOME/config`. Supports one MAC address per line in any standard format (`00:11:22:33:44:55`, `00-11-22-33-44-55`, `0011.2233.4455`, `001122334455`), with comments starting with `#`, `//`, or `;`. Automatically hot-reloaded on file modification.
- Hierarchy: global

==== Policy: v4.includedMacAddrsFile (Included MAC Addresses File)
- Name: `v4.includedMacAddrsFile`
- Default: empty
- Description: Path to a file containing MAC addresses permitted to receive DHCPv4 service (allowlist). When populated, only clients with MAC addresses in this file receive service; all other requests are dropped. If an address appears in both allowlist and denylist files, exclusion takes precedence. Automatically hot-reloaded on file modification.
- Hierarchy: global

==== Policy: v4.defaultLeasetime (Default Lease Time)
- Name: `v4.defaultLeasetime`
- Default: `3600`
- Description: Default lease duration in seconds granted to DHCPv4 clients when no client lease time is requested (Option 51).
- Hierarchy: all

==== Policy: v4.pingCheckTimeout (Ping Check Timeout)
- Name: `v4.pingCheckTimeout`
- Default: `0`
- Description: Number of milliseconds to wait for an ICMP ping response before offering an unassigned IPv4 address to a client. When set to `0` (default), ping check is disabled.
- Hierarchy: global

=== High Availability

Jagornet DHCP Server provides native Active/Standby high availability designed for enterprise resilience without requiring external cluster managers (like Corosync or Pacemaker).

[source]
----
     +------------------------+                     +------------------------+
     |     Primary Server     |   gRPC Replication  |     Backup Server      |
     |   (Active Processor)   | <=================> |   (Hot Standby Peer)   |
     +------------------------+       (mTLS)        +------------------------+
                 |                                               |
                 +-----------------------+-----------------------+
                                         |
                                         v
                            +------------------------+
                            |  Network Relay Agents  |
                            | (Relay to BOTH servers)|
                            +------------------------+
----

==== Operational Mechanics

* **Lease Replication via gRPC:** The Primary processes client requests and replicates lease updates to the Backup over high-speed gRPC (port `9066`) secured with Mutual TLS (mTLS).
* **Failure Detection:** The Backup continuously polls the Primary at `ha.pollSeconds` (default: 30s). If the Primary fails to respond after `ha.pollReplyFailureCount` attempts (default: 5), the Backup transitions to the active state and begins serving client leases.
* **Failback & Synchronization:** When the Primary recovers, it automatically synchronizes changed leases from the Backup before taking over lease handling for each subnet link.
* **Router Relay Recommendation:** For seamless failover, configure DHCP relay agents on switches/routers with the IP addresses of **both** servers (e.g. `ip helper-address 10.0.0.10` and `ip helper-address 10.0.0.11`).

==== High Availability Configuration Example

.Primary Server Configuration (`dhcpserver.yaml` on 10.0.0.10)
[source,yaml]
----
policies:
  policyList:
  - name: "ha.role"
    value: "primary"
  - name: "ha.peerServer"
    value: "10.0.0.11"
  - name: "ha.peerPort"
    value: "9066"
  - name: "ha.bindingUpdateMode"
    value: "sync"
----

.Backup Server Configuration (`dhcpserver.yaml` on 10.0.0.11)
[source,yaml]
----
policies:
  policyList:
  - name: "ha.role"
    value: "backup"
  - name: "ha.peerServer"
    value: "10.0.0.10"
  - name: "ha.peerPort"
    value: "9066"
  - name: "ha.bindingUpdateMode"
    value: "sync"
----

NOTE: In the event of catastrophic failure or database corruption on the Primary, the Primary can be forced to synchronize all leases from the Backup by deleting the state database file defined by `ha.stateDbFile` before restarting.

Several policies are available to configure High Availability (HA) behavior.

==== Policy: ha.role (HA Role)
- Name: `ha.role`
- Description: High Availability (HA) node role:

* `primary` - active server processing client requests and replicating to peer
* `backup` - standby server monitoring primary and ready for hot failover

- Hierarchy: global

==== Policy: ha.protocol (HA Protocol)
- Name: `ha.protocol`
- Default: `grpc`
- Description: Inter-node communication protocol used for High Availability lease synchronization and heartbeat polling:

* `grpc` - high-speed gRPC over TLS using Mutual TLS (mTLS) certificates (recommended)
* `rest` - legacy HTTP REST endpoints using username/password basic authentication

- Hierarchy: global

==== Policy: ha.bindingUpdateMode (HA Binding Update Mode)
- Name: `ha.bindingUpdateMode`
- Default: `sync`
- Description: The High Availability lease update synchronization mode:

* `sync`: synchronous - update the peer before responding to the client
* `async`: asynchronous - update the peer in the background while responding immediately to the client
* `database`: delegate binding updates to database cluster/replication technology

- Hierarchy: global

==== Policy: ha.peerServer (HA Peer Server)
- Name: `ha.peerServer`
- Description: The IP address or hostname of the remote High Availability peer server.
- Hierarchy: global

==== Policy: ha.peerPort (HA Peer Port)

=== REST API
The REST API is enabled by default over HTTPS port 9067 on the server host. See
startup options for controlling the port or network interfaces used for HTTPS. The
API is hosted at `https://<server-ip>:9067`.

NOTE: The `/dhcpleases` endpoints for external REST API clients are read-only (`GET`).
Lease synchronization mutations (`PUT`, `POST`) are strictly restricted to the internal
High Availability peer role (`ha.peerUsername` / `ha.peerPassword`), returning `403 Forbidden`
for standard REST API users. Arbitrary lease deletion (`DELETE`) is disabled.

Please view the Open API 3.0 documentation in the Swagger Editor:

https://editor.swagger.io/?url=https://raw.githubusercontent.com/jagornet/dhcp-docs/main/openapi.yaml[View Jagornet DHCP Server Open API docs in Swagger Editor]

=== Observability: Prometheus Metrics

Jagornet DHCP Server provides an embedded Prometheus `/metrics` endpoint over HTTPS for real-time telemetry, capacity planning, and alerting.

* **Endpoint:** `https://<server-ip>:9067/metrics`
* **Authentication:** Protected with HTTP Basic Authentication using the configured `rest.api.username` and `rest.api.password`.

==== Example Prometheus Scrape Configuration (`prometheus.yml`)

[source,yaml]
----
scrape_configs:
  - job_name: 'jagornet-dhcp'
    scheme: https
    tls_config:
      insecure_skip_verify: true   # Set to false if using enterprise CA certificates
    basic_auth:
      username: 'jagornet'
      password: 'your-secure-password'
    static_configs:
      - targets: ['dhcp1.example.com:9067', 'dhcp2.example.com:9067']
----

==== Exported Metrics Overview

* **Lease Allocation:** Active lease count, pool utilization percentage, and available addresses per subnet link.
* **Traffic Rates & Counters:** DHCPDISCOVER, DHCPOFFER, DHCPREQUEST, DHCPACK, and DHCPNAK messages.
* **DHCPv6 Counters:** SOLICIT, ADVERTISE, REQUEST, CONFIRM, RENEW, REBIND, and REPLY messages.
* **Server Health:** JVM heap memory, garbage collection duration, and Netty event loop thread performance.
